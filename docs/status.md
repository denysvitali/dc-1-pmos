# Hardware support status — Daylight DC-1 (`jagar`)

Status of the mainline-based kernel port this repository packages. "Works"
means it has functioned on real hardware in earlier bring-up; it does **not**
mean the artifacts built by any given CI run were booted — releases carry
`hardware_verified=false`, and CI only proves the build compiles.

| Component | Status | Notes |
| --- | --- | --- |
| Display | Works | DSI panel; Wayland sessions (Sway, GNOME) run. Blank/unblank works: a DPMS off stops the pipeline at the proven boundary and a DPMS on replays the handoff (`production power sequence complete` → `first DSI frame complete`) in ~0.6 s, verified on device 2026-08-16. The frontlight is not the panel's DRM backlight — our mainline DT has no panel node, so DRM exposes no `panel orientation` property and no backlight phandle — so `dc1-screen-backlight` mirrors the connector's DPMS state onto both RT4539 `bl_power` files; without it a blanked panel stays evenly lit and reads as a wedged display. |
| GPU | Works | Mali-G57 MC2 via Panfrost. |
| Touchscreen | Works | ILI2910, 10-point multitouch. |
| On-device UI | Works | Installer: touch UI (`dc1-ask`) drawn by PID 1, hardware-verified to boot and serve its menu. Desktop: GNOME Mobile on the panel, hardware-accelerated via Panfrost — no Flutter shell, no first-boot onboarding. |
| Frontlight | Works | Dual RT4539 backlight drivers: `lcd-backlight` (white, i2c-5) and `lcd-backlight-amber` (amber, i2c-2). GNOME binds exactly one backlight device to the internal display — `gsd-power` takes the first `firmware` > `platform` > `raw` match, which is always the white one — so its Settings slider drives white alone. The amber channel gets its own quick-settings slider from the `dc1-warmth@denv.it` shell extension shipped in the device package: it holds amber at a chosen share of the white level, so it behaves as a colour temperature and the tint survives brightness changes. Writes go through logind's `Session.SetBrightness`, no root needed. |
| Power key | Works | Opens GNOME's power menu (restart / power off). It does **not** blank: gnome-shell-mobile grabs the key as a mutter keybinding — so logind's `HandlePowerKey=ignore` never applies — and its `powerManager.js` maps `power-button-action='nothing'` onto `'blank'`, so `'interactive'` is the only value that avoids a screen-off. Blanking itself is recoverable (press again), but the shell re-blanks a woken screen after a hardcoded 10 s whenever the screen shield is up, which is why `lock-enabled` is shipped false. |
| Wi-Fi | Works | MT7902 via mainline mt7921s. Confirmed on device 2026-08-15: firmware loads, `wlan0` appears, and a scan returns a dozen networks. Needs `CONFIG_FW_LOADER_COMPRESS_ZSTD` — linux-firmware ships the three MT7902 blobs `.zst`-compressed, and without it the loader reports `-2` for a file that is present, `hardware init failed`, and no `wlan0`. Carried by the pinned kernel since `ea54394`. |
| Bluetooth | Works | MT7902, same upstream firmware. |
| USB gadget | Works | Serial console, USB ethernet, SSH over USB, built by `dc1-usb-gadget` (CDC-ECM + 2x CDC-ACM on `musb-hdrc.1.auto`). It must be the **only** UDC owner: `usb-signaller` (from `postmarketos-usb-moded`) starts afterwards, cannot classify our functions, tries to switch the UDC to its own developer-mode gadget, and wedges in configfs — observed on 2026-08-16 sitting in D state from boot, blocking every later configfs access and the suspend freezer with it. The device package masks `usb-signaller` and its three mode units. Teardown is ordered (unbind UDC → drop function links → `rmdir` bottom-up), never `rm -rf`: an out-of-order configfs removal is what hangs uninterruptibly. |
| Internal storage | Works | UFS. |
| Battery | Partial | Real current, charge and state of charge, from the MT6366 PMIC's FGADC coulomb counter (`mt6358-fg`) — it measures pack current through the sense element and integrates it in hardware. Verified on device 2026-08-16: capacity held at 32% across idle → 8 cores busy → idle while `current_now` tracked -126 → -245 → -128 mA, and charge integration came within 1% of the measured current over 60 s. Caveats: the state of charge is seeded from open-circuit voltage at boot (so it is re-seeded on every reboot) and measured against *design* capacity, since nothing here learns a real full-charge capacity. The pack's BQ78Z100 — which does all of that properly and persistently — still does not answer: every `bq27xxx-battery` read of `7-0055` returns `-ENXIO`. The bus is not the problem: the RT9471 at `0x53` on the same i2c-7 replies, a full scan finds only `0x53`, `0x55` NAKs both read and write addressing across 60 retries, and the bus measures 49.2 kHz against the 50 kHz the DT asks for. The vendor 5.10 tree was compared line by line — same bq27xxx glue, same pad tuning (RSEL_111 1k pull-up, applied and read back in hardware), byte-identical pinctrl rsel tables, equivalent controller quirks and AC timing — so nothing in software distinguishes us from the kernel that read `capacity 100` from that address. `mt6358-fg` stands aside automatically if the pack gauge ever reports `present=1`. Tracked as P7.1, now a hardware item: the pack connector's SMBus pair, or the gauge's own I²C block. |
| Suspend/resume | In progress | s2idle aborted with `Freezing user space processes failed after 20.001 seconds (2 tasks refusing to freeze)`, twice per attempt, returning with the panel dark. Root-caused on 2026-08-16: the unfreezable tasks are not a suspend bug at all but `usb-signaller` stuck in `unlinkat(…, AT_REMOVEDIR)` on configfs (see USB gadget above), plus whatever later touched configfs and inherited its D state — an uninterruptible task can never be frozen. Masking `usb-signaller` removes the blocker; the freezer has not yet been re-tested on a boot without it. The sleep targets stay masked (so logind answers `CanSuspend=no` and GNOME cannot offer a suspend that may still fail) until an actual suspend/resume cycle is observed on hardware. Note the kernel is built with `# CONFIG_KALLSYMS is not set`, so freezer call traces print raw addresses and cannot be symbolised — enable it before chasing any deeper suspend failure. |
| Audio | In progress | The MT6789 AFE now probes on hardware for the first time (46 DAIs registered, 2026-08-17), which took unblocking four things the shipped LK device tree gets wrong. **Power:** the AFE asks the flat legacy SCPSYS node for `MT6789_POWER_DOMAIN_AUDIO` and nothing provides it — the bootloader-handoff provider publishes DISP alone, because DISP is handed over powered and AUDIO is not (SPM `PWR_STATUS`/`PWR_STATUS_2ND` bit 22 both read 0 on a booted device). The AFE waited out the deferred-probe window and failed `-110`, so the machine card never got its platform component and there was no card at all. A bridge in the shape of the existing GPU one (`mt6789-live-audio-overlay` + its overlay, loaded by `dc1-audio`) hangs a nested provider carrying only that domain off the same node and retargets the AFE at it; the domain is registered off and the AFE's runtime PM powers it up. **Clocks:** that node numbers `topckgen` with the vendor BSP's IDs, not the ones `clk-mt6789-topckgen` registers — `top_mux_audio` (BSP 22) lands on our `CLK_TOP_APLL2_D8`, `top_clk26m_clk` (BSP 130) on an I2S mux — so the AFE reparented the wrong clocks and died with `clk_set_parent top_mux_audio-top_clk26m_clk fail -22`, leaving `runtime_status=error` and a cache-only regmap. The overlay restates the whole `clocks` array with our IDs. **Registration:** with that fixed the card still failed `-16`, from a DAPM read of the volatile `AFE_AUD_PAD_TOP` against that cache-only regmap; this port registers its ASoC component after going cache-only, where upstream's mt8186 holds a runtime-PM reference across the registration. Fixed the same way. Also fixed: the RT9101 speaker amplifier behind the codec's headphone buffers, which the machine driver described in DT but never drove — it now follows the factory sequence (VIBR up, GPIO158/159 high, 22 ms, audio, and the reverse on the way down), gated behind the `Ext_Speaker_Amp` switch. **VIBR regulator of_node (2026-08-17):** after all those fixes the machine driver (`soc:sound`) still failed to bind — it entered `mt6789_mt6366_dev_probe()` at every deferred-probe tick but produced no further output, not even `snd_soc_register_card fail`. Root cause: the stock DT in `vendor_boot` names the VIBR LDO `ldo_vibr` (hardware style) while the MT6366 regulator descriptor uses `of_match = "vibr"` (logical style), so the standard `of_match` lookup can't find a child node and registers VIBR without `rdev->dev.of_node`. `devm_regulator_get_optional()` for `extamp-supply → ldo_vibr` therefore receives -EPROBE_DEFER every time (provider exists in DT but no registered regulator has a matching of_node), which the machine driver's `mt6789_mt6366_extamp_init()` propagates silently. Extended the `regulator-name` fallback already used for `buck_vgpu`/`ldo_vsram_gpu` to cover VIBR as well; `mt6358_find_regulator_name_fallback()` now matches `ldo_vibr` via its `regulator-name = VIBR` property and sets `config.of_node` correctly. **On our mainline DT this workaround is not needed** (VIBR is declared with the logical `vibr` node name), so it is a transitional fix while `vendor_boot` still carries the stock DT. Not Works yet: awaiting hardware verification of the sound card. |
| Sensors | In progress | The accelerometer is reachable from the AP, and the previous entry here — "a DT node + defconfig entry cannot expose them, this needs a mainline mt6789 SCP/sensorhub bring-up" — is **retracted**. The sensors do hang off the SCP's two I²C buses, but both pin pairs are dual-function, so the AP's own controllers can take them: GPIO142/143 are `SCP_SCL1/SDA1` in function 2 and `SCL6/SDA6` (i2c6) in function 1, GPIO132/133 are `SCP_SCL0/SDA0` and `SCL1/SDA1` (i2c1). Measured on device 2026-08-16 by re-muxing the pins and bit-banging them through `/dev/gpiochip0`: i2c6 carries the mCube **MC3416 accelerometer at 0x4c**, which answers normally and returns a stationary 1.00 g vector from its 16-bit registers; i2c1 carries an **ambient-light/proximity part at 0x49**. Taking the buses is safe because nothing drives the SCP — no mainline driver binds `mediatek,mt6789-tinysys-scp`, and the accelerometer was found in its power-on STANDBY state, so `scp_a.img` had never initialised it. Kernel commits `d8b24985b` (DTS: i2c6 + `accelerometer@4c`), `c4dc49faa` (driver: `mcube,mc3416` 16-bit registers), and `e77962ed3` (defconfig) are now pinned (kernel pkgrel=21, 2026-08-17). The IIO device will appear once `vendor_boot` carries our mainline DTB — also landing in the same release (device pkgrel=33). Not yet marked Works: pending a hardware boot of pkgrel=21+33 confirming `iio:device* name=mc3416`, `iio-sensor-proxy`, and GNOME auto-rotation. The ALS has no mainline driver and stays undeclared. Still no gyro or magnetometer; the hall switch (magnetic lid) is AP-wired and still not in the DTS. |
